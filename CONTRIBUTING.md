# Contributing

Everyone is welcome to contribute! The simplest way is by opening [issues](https://github.com/JuliaDocs/DocumenterCitations.jl/issues) to report bugs or request features. This page details the guidelines that should be followed when contributing code to this package.


## Pull Requests

The best way to contribute code is by opening a Pull Request (PR) that fixes a bug or implements a new feature. Before opening a PR for a non-trivial change, consider first discussing it via an issue, so that a good design can be agreed upon.

To make a good PR, follow these guidelines:

* Add an adequate description to the PR, citing any corresponding issue by using `#` and the issue number. Keep in concise, and do not let an LLM submit the PR for you.
* Ensure all tests pass locally before opening the PR (see [Testing](#testing)). Continuous integration will also run the full test suite on Linux and Windows, against both the latest Julia release and the oldest supported version (the lower `[compat]` bounds in `Project.toml`).
* Reflect any change or new feature in the documentation, and make sure the documentation builds locally without errors (see [Building the Documentation](#building-the-documentation)).
* Add a note for any user-facing change to the `[Unreleased]` section of [`NEWS.md`](NEWS.md), linking to the PR or issue number.
* Format all source code with [JuliaFormatter](https://github.com/domluna/JuliaFormatter.jl) (see [Style Guide](#style-guide)). Adherence to the code style is checked automatically in continuous integration.
* Allow the "edits from maintainers" option on your PR.
* Feel free to tag (with `@`) one of the maintainers to request a review when your PR is ready.
* Do not submit "drive-by" PRs generated by an LLM or agentic coding tool. As a PR author, you must have a full understanding of the PR, and it must be based on your ideas and insights. Feel free to use an LLM to improve your work, but do not vibe-code.


### How maintainers merge pull requests

* PRs can be merged by anyone with commit access.
* PRs by authors with commit access may be self-merged after approval from a (co-)maintainer, or directly (without review) for trivial PRs.
* PRs are merged following the pattern described in the [README of the `git-merge-pr` script](https://github.com/goerz/git-merge-pr?tab=readme-ov-file#introduction). That is, a PR is rebased onto the current `master`, preserving a clean history or squashing an unclean one, and then merged with a merge commit (the `Merge #NN from …` commits in the history). That merge commit is a good place to apply editorial changes and to add a `NEWS.md` entry if the PR did not.


## Testing

The package is developed against a dedicated test environment in the [`test/`](test/) subfolder, which has its own `Project.toml` and which `develop`s the local package. This way, the development tooling (test runner, code formatter, documentation builder, coverage tooling) all share a single environment that uses the current checkout. The [`devrepl.jl`](devrepl.jl) script sets up and activates this environment.

The recommended workflow uses the [`Makefile`](Makefile) (run `make help` to see all targets). On systems without `make`, the underlying commands can be read directly from the `Makefile`.

### How to manually run tests

* Run the full test suite in a subprocess with a coverage summary:

  ```
  make test
  ```

* Or, start an interactive development REPL and run the tests from there:

  ```
  make devrepl
  ```

  This loads `Revise`, `JuliaFormatter`, and `LiveServer`, and prints a list of available commands (`help()` to show it again). Inside the REPL:

  - `include("test/runtests.jl")` — run the entire suite in-process (with `Revise` active, this picks up edits to `src/` automatically).
  - `test()` — run the suite in a fresh subprocess with coverage (equivalent to `make test`; coverage data can only be collected in a subprocess).
  - To run a single test file, include it directly, e.g. `include("test/test_formatting.jl")`. Each `test/test_*.jl` file is self-contained and is wrapped in a `@safetestset` in `runtests.jl`.
  - `show_coverage()` — print a per-file coverage table from existing coverage data.
  - `import DocumenterCitations; doctest(DocumenterCitations)` — run the docstring doctests.

Use `make clean` to remove coverage and build artifacts, or `make distclean` to restore a clean checkout.

### How to use `run_makedocs`

Many tests need to run a full Documenter build and inspect the result. The helper [`test/run_makedocs.jl`](test/run_makedocs.jl) defines `run_makedocs` for exactly this. It copies a fixture documentation tree into a temporary folder, runs `makedocs` there with its output captured, and hands the result to a `do` block:

```julia
run_makedocs(
    splitext(@__FILE__)[1];  # fixture folder next to the test file
    plugins=[CitationBibliography("refs.bib")],
) do dir, result, success, backtrace, output
    @test success
    # `dir`       – the temp folder, containing the `build/` output
    # `result`    – the return value of `makedocs`
    # `success`   – whether the call succeeded
    # `backtrace` – backtrace of any thrown exception
    # `output`    – captured STDOUT of the build
end
```

The fixture inputs (and any expected-output files) for a test live in the `test/test_*/` subdirectory next to the corresponding `test/test_*.jl` file. Pass `check_success=true` or `check_failure=true` to have an unexpected outcome logged as an error (you must still `@test success` yourself inside the block). To see the captured output of every build, set `ENV["JULIA_DEBUG"] = Main` in the dev REPL (or `JULIA_DEBUG=Main` in the environment).


## Building the Documentation

The documentation is built from the separate [`docs/`](docs/) environment, which also serves as a showcase for the package.

* Build the HTML documentation into `docs/build`:

  ```
  make docs
  ```

* Build and live-serve the documentation, auto-rebuilding on changes, at <http://localhost:8000>:

  ```
  make servedocs
  ```

  (Use `make servedocs PORT=…` to choose a different port.) You can also call `servedocs()` from within `make devrepl`.

* Build the PDF (LaTeX) version of the documentation:

  ```
  make pdf
  ```

Link checking is the slowest part of building the documentation and is disabled in the interactive REPL (the `DOCUMENTER_CHECK_LINKS=0` environment variable, set by `devrepl.jl`). It runs in continuous integration.


## Semantic Versioning

This package follows [Semantic Versioning](https://semver.org). Note that, per the [Julia convention](https://pkgdocs.julialang.org/v1/compatibility/#Version-specifier-format), pre-1.0 `0.y.z` releases treat `y` as the major (breaking) version.

The public API is what is documented in the [stable documentation](https://juliadocs.github.io/DocumenterCitations.jl/) and the docstrings of exported names. The internal fields of `CitationBibliography` and other names marked as internal are explicitly *not* part of the public API and may change in any release.

All notable changes are recorded in [`NEWS.md`](NEWS.md), which follows the [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) format.


## Release Process

Releases are made by the package maintainer only.

* [ ] Create a `release-x.y.z` branch.
* [ ] Create a single "release commit":
    * [ ] Move the `[Unreleased]` entries in `NEWS.md` into a new section for the release, and update the comparison links at the bottom of the file.
    * [ ] Set the version number in `Project.toml`, removing the `-dev` suffix (or bumping as appropriate).
* [ ] Push the `release-x.y.z` branch, but do *not* open a pull request.
* [ ] Comment `@JuliaRegistrator register` on the release commit.
* [ ] Wait for the registration to go through, for [TagBot](https://github.com/JuliaRegistries/TagBot) to tag the commit, and for the documentation to be built and deployed.
* [ ] Merge the `release-x.y.z` branch into `master` with a merge commit that bumps the version to the next `+dev`:
    * [ ] `git merge --no-ff --no-commit release-x.y.z`
    * [ ] Update `Project.toml` to `x.y.(z+1)+dev` (or as appropriate).
    * [ ] `git commit -m "Bump version to x.y.z+dev"`
* [ ] Push `master` and delete the release branch (`git branch -D release-x.y.z && git push origin :release-x.y.z`).


## Style Guide

Follow the style of the surrounding text when making changes. When adding new features please try to stick to the following points whenever applicable.

### Julia

The Julia code in this package is automatically formatted with [JuliaFormatter](https://github.com/domluna/JuliaFormatter.jl) using the settings in [`.JuliaFormatter.toml`](https://github.com/JuliaDocs/DocumenterCitations.jl/blob/master/.JuliaFormatter.toml).

To locally apply the code style, run `make codestyle`, or, if you cannot use `make`, by running

```
julia --project=test
julia> using JuliaFormatter
julia> format(["src", "docs", "test"])
```

in the project root.

Moreover:

* No blank lines at the start or end of files;
* use `function ... end` when a method definition contains more than one toplevel expression;
* related short-form method definitions should have a single blank line between them;
* unrelated or long-form method definitions must have a two blank lines separating each one;
* explicit `return` should be preferred except in short-form method definitions;
* avoid dense expressions where possible e.g. prefer nested `if`s over complex nested `?`s;
* do not use multiline comments (`#=` and `=#`);
* wrap long lines as near to 92 characters as possible, this includes docstrings.


### Markdown

* Use unbalanced `#` headers, i.e. no `#` on the right hand side of the header text;
* include a single blank line between toplevel blocks and two blank lines before `##` headers;
* do not hard wrap lines;
* use emphasis (`*`) and bold (`**`) sparingly;
* always use fenced code blocks instead of indented blocks;
* follow the conventions outlined in the Julia documentation page on documentation.


### Citation examples

* When adding entries to the `.bib` file used for the Documentation in `docs/src/refs.bib`, preferably use examples that are connected to quantum physics, especially quantum control. This is a whimsy reflecting the origins of DocumenterCitations 1.0 as a backport of the [QuantumCitations](https://github.com/JuliaQuantumControl/QuantumCitations.jl/tree/master) package.

* Use the [getbibtex](https://github.com/goerz/getbibtex) script to generate clean BibTeX entries from a DOI.
* Do not include unnecessary fields
* Use string macros for journal names
